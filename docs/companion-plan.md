## Problem Statement

Hoy el bot es reactivo: mensaje → LLM + tools → respuesta. Casi no te conoce de verdad: las notas son puntuales, no hay diario ni agenda, no ingiere correo/imágenes, y no autogestiona tu día.

Quieres un **compañero personal** que:

1. **Capture lo que vas hablando** — no un log cronológico ciego, sino hechos relevantes **por categoría** (trabajo, salud, proyectos, gente, …). Ejemplo: “ya he hablado con los del trabajo” → lo guarda donde toque y lo usa en resúmenes / contexto futuro.
2. **Te conozca mejor con el tiempo** — memoria viva para resúmenes, decisiones y proactividad.
3. Tenga **diario** y **agenda**: volcar la vida en distintas formas (chat, imágenes, Gmail, voz más adelante) y que eso se **autogestione** para ayudarte en el día a día.
4. Ejecute **skills** vía **comandos** y chat libre; flujo **brainstorm → planificar → ejecutar**.
5. Sea **proactivo** (crons: digest mail 9am, sueño/consolidación 3am, briefings…).
6. Lleve **misiones** largas en background.
7. ~~Código/git desde el móvil~~ → **fuera de Kore** (proyecto aparte).
8. **Tareas en el propio sistema** (no ClickUp por ahora).
9. Más adelante: voz, UI web, PDFs, calendar sync externo si hace falta.

## What Makes This Cool

No es “otro chatbot”. Es un **segundo cerebro operativo** con tres velocidades:

- **Chat** — charleta, brainstorm, captura al vuelo
- **Comandos** — acciones concretas ya definidas
- **Misiones + sueño + crons** — trabaja y organiza cuando tú no miras

El wow: le sueltas la vida en pedazos (texto, foto, mail) y te la **clasifica, resume y usa** sin que tengas que mantener un Notion a mano.

## Constraints

- Canal principal hoy: Telegram. Consola web Phase 1.5: **Vite+React** (chat texto + tareas v1; voz después).
- Modelo: pasar a **MIMO (multimodal)** vía OpenRouter para texto + imágenes; configurable por env.
- Deploy: Fly.io, 1 máquina pequeña, volumen `/data`.
- Contenedor desechable OK; **proteger volumen `/data`** (memoria/diario).
- Un solo usuario (`chat_id` whitelist).
- Skills = *cómo*; comandos = *disparo*. Catálogo de skills en system prompt.
- **Rename de producto** pendiente (código/Fly/Telegram pueden seguir con nombre viejo hasta decidir).
- ClickUp: existe en el código; **fuera de alcance cercano** (no usarlo como fuente de tareas).

## Premises

1. Kernel primero, integraciones después. → **ACCEPTED**
2. Skills = archivos markdown en git con frontmatter. → **ACCEPTED**
3. SQLite = verdad operativa; vault = exports legibles por categoría / diario / agenda. → **ACCEPTED**
4. Git/shell con whitelist + confirmación en acciones destructivas. → **ACCEPTED**
5. Proactividad = scheduler + misiones, no spam espontáneo del modelo. → **ACCEPTED**
6. Todo input relevante (chat, imagen, mail) puede convertirse en **entrada de memoria categorizada**, ítem de diario o evento de agenda. → **ACCEPTED**

## Approaches Considered

### Approach A — descartado

No aplica como camino: el alcance (diario, categorías, misiones, Gmail, git) exige kernel, no parches.

### Approach B: Companion kernel — **ELEGIDO**

Kernel: `prompts/`, `skills/`, scheduler, memory categórica, diario/agenda, missions. Telegram como canal. Skills `.md`; comandos vía frontmatter. System prompt ensamblado.

- Effort: L · Risk: Med
- Pros: Encaja Skill vs Comando; escala a Gmail/sueño/misiones/UI; git-friendly.
- Cons: Más estructura upfront.
- Reuses: webhook, tool loop, MemoryStore (evoluciona a categorías), Fly volume. ClickUp tools se dejan dormidos o se retiran en un PR limpio.

### Approach C: Agent platform — no

Overkill para 256MB / un usuario.

## Recommended Approach

**B**, por fases. Phase 0–1 = kernel + captura categórica + diario básico + skill hora + historial. Luego Gmail OAuth + digest. Tareas locales en cuanto el diario/memoria estén vivos.

## Arquitectura objetivo

```
Telegram (texto, fotos, luego voz)
        │
        ▼
   app/telegram (auth, chat_id, typing, media download)
        │
        ▼
   Companion Kernel
   ├── PromptAssembler (system + personality stub + skills + time + memory digests)
   ├── SkillRegistry (skills/*.md)
   ├── CommandRouter
   ├── LLM loop (MIMO multimodal + tools)
   ├── Memory (categorías + diario + agenda + sesiones)
   ├── Scheduler (Europe/Madrid)
   └── MissionRunner (asyncio, concurrency=1)
        │
        ▼
   Integrations: Gmail · Git/Shell · (ClickUp dormant) · LoL opcional · PDF · …
```

**MissionRunner:** cola asyncio, max 1 misión, checkpoints SQLite, WAL. Webhook no bloquea.

### Skill vs Comando

| Concepto | Qué es | Dónde | Ejemplo |
|----------|--------|-------|---------|
| **Skill** | Cómo hacerlo + descripción | `skills/*.md` | `capture.md`, `dream.md`, `time-madrid.md` |
| **Comando** | Disparo `/…` | frontmatter `commands:` | `/hora`, `/diario`, `/dream` |
| **Tool** | Handler Python | `app/...` | `save_memory`, `add_diary_entry`, `list_tasks` |
| **Mission** | Trabajo largo | tabla `missions` | research compra PC |
| **Cron** | Trigger temporal | scheduler Madrid | 09:00 digest, 03:00 dream |

Chat libre → modelo elige skill/tools (incl. capturar memoria). Comando → inyecta body de la skill y ejecuta.

### Formato de skill (ejemplo)

```markdown
---
name: time-madrid
description: Fecha/hora actual en Europe/Madrid para timestamps correctos.
commands: [/hora]
tools: []
---
# Time Madrid

Usa siempre Europe/Madrid. Confirma el instante actual antes de planificar
deadlines o crons.
```

### Captura y memoria por categoría

No es un chat log eterno. En cada turno (o en dream), el modelo/tools deciden si algo es **memorable** y **dónde va**:

```
vault/
  memory/
    work.md          # o memory/work/*.md
    people.md
    projects/
    health.md
    preferences.md
    ...
  diary/
    2026-07-26.md    # lo que hiciste / pasó ese día
  agenda/
    2026-07.md       # eventos / recordatorios (o tabla SQLite + export)
  dreams/
  missions/
```

Regla: **SQLite indexa** (categoría, tags, source, created_at, path); **vault guarda el texto** legible. Dream (3am) reorganiza, fusiona duplicados, actualiza resúmenes por categoría y propone agenda del día siguiente.

Ejemplo de turno: usuario dice “ya he hablado con los del trabajo” → tool `save_memory(category=work, …)` y/o línea en diario del día.

### Baseline actual

Webhook Telegram, tool loop, ClickUp (a aparcar), LoL MCP, notas planas SQLite, typing refresh, Fly `/data`. Phase 0 migra notas planas → **memoria categórica + diario**.

### Modelo LLM

- Primary: **MIMO** (multimodal) vía `OPENROUTER_MODEL`.
- Imágenes Telegram: descargar → pasar al modelo (y/o guardar en vault + describir).
- Fallback créditos: `openrouter/free` (ya existe; puede no ser multimodal).

### Prompts

```
SYSTEM = base_rules
       + personality      # stub hasta que tú lo escribas
       + skills_catalog
       + time_context     # Europe/Madrid
       + memory_digests   # por categoría (top facts, no todo el vault)
       + today_diary_excerpt
       + agenda_upcoming
       + recent_session   # últimos mensajes del día
```

### Esquema SQLite (Phase 0–3)

```
memory_items(id, category, text, source, source_ref, created_at, updated_at)
diary_entries(id, day, text, source, created_at)
agenda_items(id, starts_at, ends_at, title, status, source, created_at)
tasks(id, title, status, due_at, priority, notes, created_at, updated_at)
messages(id, role, content, created_at, session_date)
sessions(session_date PK, summary, updated_at)
jobs(id, name, cron, last_run_at, last_status, last_error)
missions(id, title, status, plan_json, step_index, result_path, created_at, updated_at)
mission_events(id, mission_id, kind, payload, created_at)
```

(`notes` actual → migrar a `memory_items` category=`general` o similar.)

Historial chat: últimos **20 msgs** o ~8k tokens del **día Madrid**.

## Mapa → fases

### Phase 0 — Kernel + captura
- `prompts/system.md`, `prompts/personality.md` (stub)
- `skills/`: `time-madrid`, `capture` (memoria por categoría), `brainstorm`, `plan`, `execute`
- PromptAssembler + catálogo skills
- Comandos: `/skills`, `/hora`, `/diario`, …
- Historial sesión + MIMO en config
- Tools: `save_memory`, `add_diary_entry` (mínimo)
- Rename producto: **no bloquea** (constante/`APP_NAME` cuando lo decidas)

### Phase 1 — Diario / agenda / sueño
- Vault `memory/`, `diary/`, `agenda/`
- Cron 03:00 `dream`: consolidar categorías, resumen del día, propuestas
- `/dream` manual
- Tasks locales básicas (`tasks` table + skill/comando)
- Briefing matutino opcional

### Phase 2 — Gmail (OAuth)
- OAuth + refresh en `/data`
- Triage → carpeta no-importantes; importantes al digest
- Cron 09:00 resumen Telegram
- `/inbox`
- Hechos del mail pueden virar a `memory_items` / agenda

### Phase 3 — Misiones
- Background research/ejecución con estados y reportes parciales
- Pipeline brainstorm → plan → execute

### ~~Phase 4 — Código / git~~ — fuera de Kore
- Programar desde el móvil = **proyecto aparte** (no mezclar con este companion).
- Kore no ejecuta git/shell de desarrollo.

### Phase 5+ — Calendar externo, voz, UI, PDF
Sin hard deadline; tras el “día a día útil” (memoria + diario + mail + tasks).

## What I noticed about how you think

- El núcleo no es “más tools”: es *“todo lo que vaya hablando lo anote… por categoría”* y un diario/agenda que se autogestiona.
- Aparcar ClickUp y querer **tareas en tu sistema** alinea el producto: un solo sitio de verdad (el companion), no otro SaaS.
- Rename pendiente + personalidad “más adelante” = no bloqueas el build del kernel; bien.
- MIMO cierra el hueco multimodal sin inventar un pipeline raro de visión aparte.
